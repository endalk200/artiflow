# Secure the npm CLI Release Pipeline

Artiflow publishes the `artiflow` CLI through a Changesets release pull request and a separate npm staging workflow. The workflow first checks whether the version already exists, then runs the complete CLI release gate without an OIDC publishing identity, audits only the CLI build and test dependency closure, packs one npm tarball, verifies its exact allowlisted contents, installs and smoke-tests that same tarball, and records its checksum. Repository-wide and web-application checks remain in protected CI and are not reconfigured by the CLI publication workflow. Only a second `npm-production` job can request an OIDC token. Its executable npm CLI and release tarball are packed and checksummed by the unprivileged preparation job; the staging job only downloads, verifies, and invokes those artifacts to submit the package with `npm stage publish`. It may not publish the package directly.

The GitHub `npm-production` environment is restricted to `main`, requires explicit approval, and disallows admin bypass. The npm trusted publisher must be restricted to the `publish-npm.yml` workflow, the `npm-production` environment, and `npm stage publish`; package access must require 2FA and disallow token publishing. A maintainer reviews and approves the staged package with 2FA before publishing the matching draft GitHub Release. Protected `main` and `artiflow-cli-v*` references, pinned third-party actions, CODEOWNERS coverage, least-privilege job permissions, and a full release audit are prerequisites for distribution.

Release tags identify the exact commit whose artifact was staged. Automation must reject an existing tag that points elsewhere and must not recreate a missing release from a later commit merely because the version already exists on npm. Recovery uses the original failed workflow run or an independently verified provenance commit so npm provenance, the Git tag, and the GitHub Release cannot disagree about the release source.
